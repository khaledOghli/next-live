# Sandbox mode: running code you do not trust

[← Multi-file snippets](./14-multi-file.md) · [Docs index](./README.md)

By default next-live runs a snippet directly in your page. That is what lets a
snippet use your store, your UI kit and your live objects, and it is the right
choice when the people writing snippets are your own team.

It is the wrong choice when they are not. A public playground, code generated by an
AI model, or snippets that users share with each other all mean running code written
by strangers. Code that runs in your page can read your cookies and storage, call
your APIs as the signed-in user, and change anything on the page.

**Sandbox mode runs the snippet inside an iframe that the browser isolates from your
page.** The editor, the error display and the console panel keep working as before.

## Should you use it?

| | In the page (default) | Sandbox mode |
|---|---|---|
| Who writes the snippets | People you trust | Anyone |
| `props` | Passed by reference: stores, functions, class instances | Copied: plain data only |
| Where modules are registered | On your page | On the sandbox page |
| `'unsafe-eval'` in your page's CSP | Needed on routes that run snippets | Not needed. Only the sandbox page needs it. |
| A snippet stuck in `while (true)` | Freezes the tab | Freezes the frame, which is replaced (see [hosting](#choosing-where-to-host-the-sandbox)) |
| Setup | One component | One component and one small extra page |

If your snippets need your live store or callbacks from your page, stay in the page.
If strangers can write snippets, use the sandbox.

## How it works

1. Your page renders `<LiveProvider sandbox={{ src: '/sandbox' }}>`. It **never**
   compiles or runs the snippet itself.
2. `<LivePreview>` renders an `<iframe sandbox="allow-scripts">` that loads `src`, a
   small page you host.
3. That page calls `mountSandbox()` from `next-live/sandbox`. It compiles the code your
   page sends and renders the result.
4. The two pages talk over a private `MessageChannel`. Errors, console output and the
   content height travel back, so `<LiveError>`, `<LiveConsole>` and an auto-sized
   preview all work.

The iframe does not get `allow-same-origin`, so the browser gives it an **opaque
origin**. Code inside it cannot read your cookies, storage or DOM, even if the
sandbox page is served from your own domain.

## Step 1: Build the sandbox page

The sandbox page is where your module registry lives now, because that is where
snippets run.

### With Next.js (App Router)

Create a route for it. Keeping it in its own route group lets it skip your app's
layout, so the frame shows only the snippet.

```tsx
// app/(sandbox)/sandbox/page.tsx
import { SandboxClient } from './SandboxClient';

export default function SandboxPage() {
  return <SandboxClient />;
}
```

```tsx
// app/(sandbox)/sandbox/SandboxClient.tsx
'use client';

import { LiveSandboxRoot } from 'next-live/sandbox';
import * as ui from '@/components/ui';

const modules = { '@acme/ui': ui };

export function SandboxClient() {
  return (
    <LiveSandboxRoot
      modules={modules}
      allowedOrigins={['https://app.example.com', 'http://localhost:3000']}
    />
  );
}
```

```tsx
// app/(sandbox)/layout.tsx
export default function SandboxLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}
```

`allowedOrigins` is **required**. It lists the pages allowed to embed this sandbox and
send it code. Without it, any website could put your sandbox page in a frame and use
it. Write each origin as `scheme://host:port`, with no path and no trailing slash.

### With Vite or plain HTML

Any page that loads `next-live/sandbox` works.

```html
<!-- sandbox.html -->
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <title>Sandbox</title>
  </head>
  <body>
    <script type="module" src="/src/sandbox.ts"></script>
  </body>
</html>
```

```ts
// src/sandbox.ts
import { mountSandbox } from 'next-live/sandbox';
import * as ui from './ui';

mountSandbox({
  modules: { '@acme/ui': ui },
  allowedOrigins: ['https://app.example.com', 'http://localhost:5173'],
});
```

With Vite, add the page as a build input so it is part of the production build:

```ts
// vite.config.ts
export default defineConfig({
  build: {
    rollupOptions: {
      input: { main: 'index.html', sandbox: 'sandbox.html' },
    },
  },
});
```

If you open the sandbox page directly in a tab, it shows a short note saying it is a
sandbox. That is expected: it only does something inside a frame.

## Step 2: Point the provider at it

On the page where people edit snippets, add `sandbox`:

```tsx
'use client';

import { LiveProvider, LivePreview, LiveError } from 'next-live';
import { LiveEditor } from 'next-live/editor';
import { LiveConsole } from 'next-live/console';

export function PublicPlayground({ source }: { source: string }) {
  return (
    <LiveProvider code={source} sandbox={{ src: '/sandbox' }}>
      <LiveEditor />
      <LivePreview height="auto" title="Snippet preview" />
      <LiveError />
      <LiveConsole />
    </LiveProvider>
  );
}
```

That is the whole switch. `files` for [multi-file snippets](./14-multi-file.md) works
the same way.

The host code for sandbox mode is downloaded only when a provider actually uses
`sandbox`, so your other pages do not pay for it. To start the download early, call
`preloadSandboxHost()` from `next-live`, for example when someone hovers a link to
the playground.

## Step 3: Set the security headers

### On the sandbox page

This is the page that runs snippets, so it is the one that needs `'unsafe-eval'`, and
the one to lock down hardest. In Next.js, in `proxy.ts`:

```ts
import { NextResponse, type NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  const response = NextResponse.next();

  if (request.nextUrl.pathname.startsWith('/sandbox')) {
    response.headers.set(
      'Content-Security-Policy',
      [
        'sandbox allow-scripts',
        "default-src 'self'",
        "script-src 'self' 'unsafe-inline' 'unsafe-eval'",
        "style-src 'self' 'unsafe-inline'",
        "img-src 'self' data: blob:",
        "font-src 'self' data:",
        "connect-src 'none'",
        "base-uri 'none'",
        "form-action 'none'",
        "frame-ancestors 'self' https://app.example.com",
      ].join('; '),
    );
  }

  return response;
}
```

What the important lines do:

- **`sandbox allow-scripts`** keeps the page isolated even if someone opens it
  directly or frames it without the `sandbox` attribute.
- **`frame-ancestors`** decides which pages may embed the sandbox. List your own.
- **`connect-src 'none'`** stops a snippet from sending anything anywhere with `fetch`.
  If your snippets legitimately call an API, list that API here, and only that.
- **`'unsafe-eval'`** is required here, because this page compiles code at runtime. It
  is not needed on your main page any more.

### On your main page

Allow your page to frame the sandbox:

```ts
"frame-src 'self'", // or the sandbox's origin, if it is on another domain
```

If a page only uses sandbox mode, it can drop `'unsafe-eval'` entirely. See
[Security](./05-security.md) for the rest of the policy.

## Props are copied, not shared

In the page, `props` are passed by reference: a snippet can call a function you pass,
or change a store and see your app update. The iframe is a separate world, so props
are **copied** into it, the same way `postMessage` copies data.

That works for plain data:

- objects, arrays, strings, numbers, booleans, `null`
- `Date`, `Map`, `Set`, `RegExp`, typed arrays

It does not work for:

- functions (including event handlers like `onSave`)
- class instances with methods, such as a store
- DOM nodes and React elements

Passing something that cannot be copied shows a clear error in `<LiveError>`:

```
Props for a sandboxed preview are copied into the iframe, so they must be plain data: objects,
arrays, strings, numbers, booleans, dates, maps and sets. Functions, class instances, DOM nodes
and React elements cannot cross.
```

When your data changes, just pass new props. The component in the frame re-renders
with them, without recompiling.

## Modules live on the sandbox page

The iframe cannot use modules from your page. Register everything snippets may import
in `mountSandbox({ modules })` or `<LiveSandboxRoot modules>`. The same goes for
`scope` and `transform`.

If you pass `modules`, `scope` or `transform` to `<LiveProvider sandbox>`, they are
ignored, and next-live says so in the console during development.

## Choosing where to host the sandbox

Both options below isolate the snippet from your cookies, storage and DOM. The
difference is what happens when a snippet freezes.

**On your own site, for example `/sandbox`.** This is the easiest setup. Browsers
usually run a same-site frame in the same process as your page, though, so a snippet
stuck in `while (true) {}` freezes your page along with it.

**On a separate site, for example `sandbox-example.net`.** A different site means a
different registrable domain; `sandbox.example.com` is still the same site as
`example.com`. Chrome, Edge and Firefox run a cross-site frame in its own process, so
a frozen snippet only freezes its frame, and next-live replaces the frame (see the
next section). Safari does not split frames into separate processes.

For local development, you can get a separate site without a second server: open your
app at `http://localhost:3000` and point the sandbox at
`http://127.0.0.1:3000/sandbox`.

```tsx
<LiveProvider code={source} sandbox={{ src: process.env.NEXT_PUBLIC_SANDBOX_URL ?? '/sandbox' }}>
```

## When a snippet freezes

next-live checks that the sandbox is still responding, every 2 seconds. If it does not
answer within 5 seconds, the frame is treated as frozen: it is thrown away, a fresh one
is created, and the current code is sent again.

A snippet that freezes every time would restart forever, so after **3 freezes within a
minute** next-live stops and shows an error instead. Editing the code, or calling
`reload()`, tries again:

```tsx
import { useLiveContext } from 'next-live';

function RestartButton() {
  const { sandbox } = useLiveContext();
  if (!sandbox || sandbox.status !== 'failed') return null;
  return <button onClick={sandbox.reload}>Restart the preview</button>;
}
```

`sandbox.status` is one of `connecting`, `ready`, `unresponsive` or `failed`. The
preview wrapper also carries it as `data-next-live-sandbox`, for styling:

```css
[data-next-live-sandbox='connecting'] {
  opacity: 0.6;
}
```

## What a sandboxed snippet can and cannot do

**It cannot:**

- read your page's cookies, `localStorage`, `sessionStorage` or DOM
- call your APIs with the visitor's cookies
- navigate your page, open pop-ups or submit forms
- use the camera, microphone, geolocation, USB, payments, clipboard reading or screen
  capture
- send data anywhere, if the sandbox page uses `connect-src 'none'`

Inside the frame, `localStorage`, `sessionStorage`, `document.cookie` and IndexedDB
throw a `SecurityError`. If a snippet needs storage, give it an in-memory stand-in
through `modules`.

**It can still:**

- use CPU and memory until the watchdog replaces the frame
- draw anything inside its own box, including something that looks like a login form.
  If strangers write your snippets, make it obvious on your page that the preview is
  user content.
- reach the network, if you widen `connect-src`

To grant a capability back, such as forms or modals, use `permissions`:

```tsx
<LiveProvider code={source} sandbox={{ src: '/sandbox', permissions: ['allow-forms', 'allow-modals'] }}>
```

## Options

### `sandbox` on `<LiveProvider>`

| Option | Type | Default | What it does |
|---|---|---|---|
| `src` | `string` | required | URL of the sandbox page. A relative URL resolves against your page. |
| `permissions` | `SandboxPermission[]` | `[]` | Extra iframe permissions: `allow-forms`, `allow-modals`, `allow-popups`, `allow-popups-to-escape-sandbox`, `allow-pointer-lock`, `allow-downloads`. |
| `allowSameOrigin` | `boolean` | `false` | Give the frame its real origin (cookies, storage). Only allowed when `src` is on a different origin from your page. |
| `allow` | `string` | denies powerful features | The iframe's Permissions Policy. |
| `credentialless` | `boolean` | `true` | Load the frame without cookies, in browsers that support it. |
| `handshakeTimeoutMs` | `number` | `10000` | How long to wait for the sandbox page before reporting it unreachable. |
| `pingIntervalMs` | `number` | `2000` | How often to check the sandbox is responding. |
| `pongTimeoutMs` | `number` | `5000` | How long an unanswered check may take before the frame counts as frozen. |
| `maxHeight` | `number` | `10000` | The tallest, in pixels, the frame grows with `height="auto"`. |
| `maxRestarts` | `number` | `3` | Automatic restarts allowed within a minute before giving up. |

### `mountSandbox` and `<LiveSandboxRoot>`

Both take the same options. `mountSandbox` also accepts `container`.

| Option | Type | Default | What it does |
|---|---|---|---|
| `allowedOrigins` | `string[]` or `'*'` | required | Origins of the pages allowed to embed the sandbox. `'*'` allows every website and logs a warning. |
| `modules` | `ModuleRegistry` | `{}` | What snippets may import. |
| `scope` | `LiveScope` | `{}` | Free variables for snippets. |
| `transform` | `TransformFn` | Sucrase | A custom transpile step. |
| `maxCodeChars` | `number` | `1000000` | The largest snippet accepted, counted across all files. |
| `maxFiles` | `number` | `200` | The most files accepted in one project. |
| `onConnect` | `(info) => void` | - | Called when a page connects, with its `origin`. |
| `dangerouslyAllowSameOriginHost` | `boolean` | `false` | Run even when the embedding page has the same origin and did not sandbox the frame. For local debugging only. |
| `container` | `HTMLElement` | a new `<div>` | `mountSandbox` only: where to render. |

`mountSandbox` returns `{ dispose() }`, which disconnects and unmounts.

### `<LivePreview>` in sandbox mode

| Prop | Type | Default | What it does |
|---|---|---|---|
| `height` | `number` or `'auto'` | `'auto'` | A fixed height in pixels, or follow the snippet's content. |
| `title` | `string` | `'Live preview'` | The iframe's accessible title. |
| `loading` | `'eager'` or `'lazy'` | `'eager'` | The iframe's `loading` attribute. |
| `frameClassName`, `frameStyle` | | | Applied to the iframe element itself. `className` and `style` go on the wrapper, as usual. |
| `fallback` | `ReactNode` | the provider's | Shown over the frame until the first compile finishes. |

## Troubleshooting

### "The sandbox page at ... did not answer within 10000 ms"

The frame loaded something, but no sandbox answered. Work through the checklist in the
message:

1. **Open the sandbox URL directly in a tab.** You should see the short "this page is a
   next-live sandbox" note. A 404 or an error page means the route is wrong.
2. **Check that the page calls `mountSandbox()` or renders `<LiveSandboxRoot>`.**
3. **Check `allowedOrigins`.** It must contain your page's exact origin, including the
   port. In development the sandbox logs a warning when it ignores an origin.
4. **Check the sandbox page's `frame-ancestors`** (and remove any `X-Frame-Options`
   header). The browser console shows a "Refused to frame" message when this is the cause.
5. **Check your page's `frame-src`.**

### "sandbox.allowSameOrigin is refused because sandbox.src has the same origin as this page"

`allowSameOrigin` combined with a same-origin `src` would let the snippet remove its own
sandbox and reach your page. Either leave `allowSameOrigin` off, or serve the sandbox from
another origin.

### "Props for a sandboxed preview are copied into the iframe"

A prop is a function, a class instance or something else that cannot be copied. See
[Props are copied, not shared](#props-are-copied-not-shared).

### "This page runs next-live X, but the sandbox page runs next-live Y"

The two pages must use the same next-live version. Deploy them together.

### The frame stays blank in development

- **Vite:** module scripts loaded by a sandboxed frame need CORS. If the browser console
  shows a CORS error, allow it for the dev server: `server: { cors: { origin: '*' } }`.
- **Next.js:** under `next dev` the frame stays blank, `<LiveError>` reports that the
  sandbox did not answer, and the terminal logs "Blocked cross-origin request to
  Next.js dev resource". A sandboxed frame has an opaque origin, so the requests it
  makes for its own `/_next` scripts count as cross-site and carry no `Referer`, and
  `next dev` refuses them with a 403. `allowedDevOrigins` cannot fix this, because
  there is no host name to allow. Test sandbox mode against a production build
  instead, which has no such check:

  ```bash
  next build && next start
  ```

### `localStorage` throws inside a snippet

That is the isolation working. See
[What a sandboxed snippet can and cannot do](#what-a-sandboxed-snippet-can-and-cannot-do).
